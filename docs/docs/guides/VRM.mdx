# VRM and VRMA animation retargeting

VRM support is implemented on top of glTF/GLB loading. A `.vrm` file is a GLB with VRM metadata, and a `.vrma` file is an animation-only GLB that uses `VRMC_vrm_animation`.

## Asset extensions

Metro must be configured to bundle VRM and VRMA files:

```js
module.exports = {
  resolver: {
    assetExts: ['glb', 'vrm', 'vrma'],
  },
}
```

## Retargeting model

Retargeted animation targets humanoid bones, not the destination model's raw node names. The loader reads both files, creates a humanoid binding table, and applies animation to the target model's matching humanoid bones.

The animation source can be:

- `.vrma` with `extensions.VRMC_vrm_animation.humanoid.humanBones`.
- `.vrm`, `.glb`, or `.gltf` with VRM 1.0 `extensions.VRMC_vrm.humanoid.humanBones`.
- `.vrm`, `.glb`, or `.gltf` with VRM 0.x `extensions.VRM.humanoid.humanBones`.
- `.glb` or `.gltf` with an explicit `sourceHumanoidNodeNames` mapping passed to `useVRMAnimation`.

Plain glTF animation files without humanoid metadata can still be played directly with `<Animator />` when the animation is embedded in the same loaded asset. To retarget them to another VRM, pass an explicit bone mapping profile so the loader can build a source humanoid rest pose without guessing.

The metadata loader accepts both binary `.glb`/`.vrm`/`.vrma` files and JSON `.gltf` files. For JSON `.gltf` animation sources, the animation asset still needs to be loadable by the native Filament asset loader at runtime; metadata parsing alone does not resolve arbitrary external buffers or textures.

The retargeting path uses these inputs:

- Animation-source humanoid rest pose from `extensions.VRMC_vrm_animation.humanoid.humanBones`, `extensions.VRMC_vrm.humanoid.humanBones`, or `extensions.VRM.humanoid.humanBones`.
- VRM 1.0 humanoid rest pose from `extensions.VRMC_vrm.humanoid.humanBones`.
- VRM 0.x humanoid rest pose from `extensions.VRM.humanoid.humanBones`.
- Source and target local/world rest rotations for each bound humanoid bone.

Use `useVRMAnimation` to load the metadata required by `VRMAnimationRetargeter`. The hook also loads the animation source as a hidden Filament asset because the native animator samples its glTF animation tracks each frame. The returned `retargeting.source` report identifies whether the source metadata came from `VRMC_vrm_animation`, VRM 1.0, VRM 0.x, or could not be identified.

```tsx
import { ModelRenderer, VRMAnimationRetargeter, useModel, useVRMAnimation } from 'react-native-filament'

const vrmSource = require('./avatar.vrm')
const vrmaSource = require('./dance.vrma')

function Avatar() {
  const model = useModel(vrmSource)
  const animation = useVRMAnimation(vrmaSource, vrmSource)

  return (
    <>
      {model.state === 'loaded' && <ModelRenderer model={model} transformToUnitCube />}
      {model.state === 'loaded' && animation.sourceAsset != null && animation.retargeting != null && (
        <VRMAnimationRetargeter
          sourceAsset={animation.sourceAsset}
          targetModel={model}
          bindings={animation.retargeting.bindings}
          expressionBindings={animation.retargeting.expressionBindings}
          expressionMaterialColorBindings={animation.retargeting.expressionMaterialColorBindings}
          expressionTextureTransformBindings={animation.retargeting.expressionTextureTransformBindings}
          expressionOverrideBindings={animation.retargeting.expressionOverrideBindings}
          lookAtBoneBindings={animation.retargeting.lookAtBoneBindings}
          lookAtExpressionBindings={animation.retargeting.lookAtExpressionBindings}
          nodeConstraintBindings={animation.retargeting.nodeConstraintBindings}
          springBoneBindings={animation.retargeting.springBoneBindings}
          targetVersion={animation.retargeting.targetVersion}
        />
      )}
    </>
  )
}
```

`targetVersion` is part of the retargeting result because VRM 0.x targets need a different axis conversion from VRM 1.0 targets.

For ordinary glTF animation sources without VRM metadata, provide a stable `sourceHumanoidNodeNames` mapping. This is the intended path for BVH-to-glTF or third-party motion pipelines where the source skeleton names are known:

```tsx
const sourceHumanoidNodeNames = React.useMemo(
  () => ({
    hips: 'Hips',
    spine: 'Spine',
    chest: 'Spine1',
    neck: 'Neck',
    head: 'Head',
    leftUpperArm: 'LeftArm',
    leftLowerArm: 'LeftForeArm',
    leftHand: 'LeftHand',
    rightUpperArm: 'RightArm',
    rightLowerArm: 'RightForeArm',
    rightHand: 'RightHand',
    leftUpperLeg: 'LeftUpLeg',
    leftLowerLeg: 'LeftLeg',
    leftFoot: 'LeftFoot',
    rightUpperLeg: 'RightUpLeg',

    rightFoot: 'RightFoot',
  }),
  []

const animation = useVRMAnimation(glbMotionSource, vrmSource, { sourceHumanoidNodeNames })
```


## VRM 0.x axis compatibility

VRM 0.x and VRM 1.0 do not use the same forward-facing convention. VRM 0.x requires the model to face `-Z`, while VRM 1.0 T-pose defines the visible model as facing `+Z`.

When applying a VRMA animation to a VRM 0.x target, the animation values need the same compatibility conversion used by `@pixiv/three-vrm-animation`:

- Quaternion rotation tracks: negate the `x` and `z` components.
- Hips translation tracks: negate the `x` and `z` components.
- Do not apply this conversion to VRM 1.0 targets.

In quaternion form:

```ts
function convertVRM0Rotation([x, y, z, w]) {
  return [-x, y, -z, w]
}
```

In translation form:

```ts
function convertVRM0HipsTranslationDelta([x, y, z]) {
  return [-x, y, -z]
}
```

This conversion is intentionally target-version dependent. Applying it globally will make VRM 1.0 models such as Seed-san incorrect, while omitting it makes VRM 0.x models show mirrored or reversed upper-limb motion.

## Example pages

The example app keeps VRM checks split by page, following the rest of the sample project:

- `VRMModel`: a focused Seed-san page for quick VRM 1.0 animation and runtime-extension checks.
- `VRMCrossTest`: cross-tests multiple avatars against multiple external VRMA motions.
- `VRMOfficialSamples`: loads the official `vrm-c/vrm-specification/samples` models as compatibility fixtures. This page does not force external VRMA retargeting because some official samples are material or expression validation panels, not skinned dance avatars.

## Validation matrix

Use more than one model and more than one motion when validating retargeting. A single model can hide a bad axis assumption because its rest pose may cancel out the error.

The current example uses:

- `Seed-san.vrm`: VRM 1.0, expected to play VRMA without VRM0 axis conversion.
- `AvatarSample_A.vrm`: VRM 0.x, expected to use VRM0 axis conversion.
- `TkVrmViewerSample.vrm`: VRM 0.x sample from `tk256ailab/vrm-viewer`, expected to use VRM0 axis conversion.
- `VRM1_Constraint_Twist_Sample.vrm`: official VRM 1.0 sample for constraint twist behavior, with 14 node constraints and 22 spring groups.
- `VRMC_materials_mtoon_UV_Animation_Test.vrm`: official VRM 1.0 sample for MToon and material UV animation compatibility.
- `VRMC_vrm_expressions_isBinary_Overridden.vrm`: official VRM 1.0 sample for expression `isBinary` and override behavior.
- `VRMC_vrm_expressions_isBinary_Overrides.vrm`: official VRM 1.0 sample for expression `isBinary` and override behavior.
- `Jump.vrma`, `Relax.vrma`, `Clapping.vrma`, and `LookAround.vrma`: VRMA motions from `tk256ailab/vrm-viewer`.

The most useful visual checks are crossed arms, foot direction, hips translation, and asymmetric hand motion. These reveal x/z sign mistakes faster than idle or small head motions.

The official VRM samples come from `vrm-c/vrm-specification/samples`. They do not include paired character motion files. `Seed-san` and `VRM1_Constraint_Twist_Sample` are useful for motion retargeting checks; `VRMC_materials_mtoon_UV_Animation_Test` and the expression `isBinary` samples are validation panels, so they should be inspected as static or self-animated compatibility fixtures instead of forced through a dance motion.

## Material fallback

VRM 1.0 files commonly use `VRMC_materials_mtoon`, `VRMC_node_constraint`, and `VRMC_springBone`. glTF renderers can load the mesh while ignoring unsupported VRM runtime extensions, but MToon materials may need a fallback to ordinary glTF materials or `KHR_materials_unlit` so the model renders completely.

Material fallback should not modify humanoid metadata used for retargeting. Read humanoid and compatibility metadata from the original VRM file, then render a patched fallback GLB only for material compatibility.

## Expressions

VRMA expressions are represented as glTF translation tracks on expression proxy nodes. The X component of the animated translation is interpreted as the expression weight.

`useVRMAnimation` returns `expressionBindings` that map those VRMA expression proxy nodes to the target VRM model's morph target binds:

- VRM 1.0: `extensions.VRMC_vrm.expressions.preset/custom.*.morphTargetBinds`.
- VRM 0.x: `extensions.VRM.blendShapeMaster.blendShapeGroups[*].binds`.
- VRM 0.x preset names are normalized to VRM 1.0 names, for example `a` to `aa`, `i` to `ih`, `blink_l` to `blinkLeft`.

The retargeter applies morph target weights each frame through Filament's renderable manager.

`useVRMAnimation` also returns `expressionMaterialColorBindings` for VRM 1.0 `materialColorBinds`. The retargeter applies them with the VRM accumulation rule: start from the material's initial value, then add each expression's `(targetValue - baseValue) * weight` contribution for the same material parameter.

`useVRMAnimation` also returns `expressionTextureTransformBindings` for VRM 1.0 `textureTransformBinds`. The retargeter applies the accumulated transform to every sampler transform parameter exposed by the material instance, using Filament's native sampler transform metadata instead of guessing parameter names.

`useVRMAnimation` also returns `expressionOverrideBindings` for VRM 1.0 procedural override rules. The retargeter applies `overrideBlink`, `overrideLookAt`, and `overrideMouth` before morph, material color, texture transform, and expression-based LookAt values are accumulated:

- `overrideMouth` affects `aa`, `ih`, `ou`, `ee`, and `oh`.
- `overrideBlink` affects `blink`, `blinkLeft`, and `blinkRight`.
- `overrideLookAt` affects `lookUp`, `lookDown`, `lookLeft`, and `lookRight`.
- `block` suppresses the target procedural expression while the overriding expression is active.
- `blend` linearly attenuates the target procedural expression by the accumulated overriding expression output weight.
- `isBinary` is evaluated before override effects are applied, matching the VRM 1.0 expression specification.

## LookAt

VRMA LookAt is represented as a rotation track on a look direction proxy node.

For VRM 1.0 targets with `lookAt.type = "expression"`, `useVRMAnimation` returns `lookAtExpressionBindings` and `VRMAnimationRetargeter` maps yaw and pitch into `lookLeft`, `lookRight`, `lookUp`, and `lookDown` expression morph target weights.

For VRM 1.0 targets with `lookAt.type = "bone"` and VRM 0.x targets with `firstPerson.lookAtTypeName = "Bone"`, `useVRMAnimation` returns `lookAtBoneBindings`. The retargeter maps yaw and pitch into `leftEye` and `rightEye` local rotations using horizontal inner/outer and vertical up/down range maps.

## Node Constraints

VRM 1.0 models can use `VRMC_node_constraint` to make secondary nodes follow another node. This is common for accessory rigs or duplicated mechanical limbs. `useVRMAnimation` returns `nodeConstraintBindings`, and `VRMAnimationRetargeter` applies supported constraints after humanoid retargeting each frame.

Currently supported:

- `rotation`: applies the source node's local rotation delta to the constrained target node, respecting the constraint weight.
- `aim`: rotates the target from its rest rotation so its configured aim axis points at the source in world coordinates.
- `roll`: transfers source roll around the configured destination roll axis, respecting the constraint weight.

Seed-san's mechanical arm is represented this way. It is not part of the humanoid bone table; the VRM declares 23 `rotation` constraints from the left shoulder, arm, hand, palm, thumb, and finger bones to matching `robo_*` nodes. This makes the accessory arm follow the humanoid animation after retargeting.

## Spring Bones

VRM 1.0 spring bones are runtime physics chains declared by `extensions.VRMC_springBone`. `useVRMAnimation` returns `springBoneBindings`, and `VRMAnimationRetargeter` applies them after humanoid retargeting and node constraints.

Currently supported:

- Spring joint chains using `stiffness`, `dragForce`, `gravityDir`, `gravityPower`, and `hitRadius`.
- Collider groups with sphere and capsule colliders.
- Optional spring `center` nodes so simulation is performed in the model's intended center space.

Seed-san uses this for hair springs and the `RoboWire` chain behind the mechanical arm.

Seed-san validation notes:

- 9 spring groups are declared.
- `RoboWire` is a 7-joint chain from `robo_wire` through `robo_wire_end`, which becomes 6 simulated segments.
- The asset declares 8 colliders in 2 collider groups.
- Hair springs use `hips` as their center node; `RoboWire` has no explicit center and is simulated in model space.

## Known gaps

The current retargeting path covers humanoid FK animation, hips translation, expression morph target weights and override rules, VRM 1.0 expression material color binds, VRM 1.0 expression texture transform binds, VRM 1.0 expression-based LookAt, VRM 1.0/0.x bone-based LookAt, `VRMC_node_constraint` rotation/aim/roll constraints, and core `VRMC_springBone` simulation. Full VRM extension support still requires broader validation against more official and third-party VRM 1.0 assets, especially models with non-humanoid accessory rigs driven by spring bones and constraints.
